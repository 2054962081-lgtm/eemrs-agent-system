01 · Problem & Opportunity

从患者就医与医生接诊流程确定产品机会

早期用户调研归纳出三类稳定问题：患者担心隐私泄露、问诊与挂号决策不方便、医生病历书写与信息整理耗时。产品目标因此收敛为：降低患者诊前表达与决策成本、减少医生接诊前的信息整理工作，同时控制敏感医疗数据的使用范围。

🧑

患者侧：缩短从描述症状到完成挂号的路径

  • 用户不知道哪些症状、病史和检查信息值得提前说明。
  • 问诊结束后仍要自行判断科室并重新进入挂号入口选择。
  • 到院后再次复述同一批信息，沟通和信息迁移成本高。
产品切入：预问诊 → 科室推荐 → 一键挂号 → 问诊信息复用
👨‍⚕️

医生侧：减少接诊前的信息整理

  • 接诊前缺少统一整理的主诉、病程和既往信息。
  • 多次检验报告需要人工逐份查看和比对。
  • 病历书写耗时，但草稿必须来源清楚、不能自动补事实。
产品切入：问诊摘要 + 趋势分析 + 结构化病历草稿
🔐

医疗场景：效率提升必须有清晰责任与数据边界

  • 医疗健康数据敏感，不能为了接入模型扩大数据暴露范围。
  • 模型输出存在波动，关键结果要能稳定复现和定位问题。
  • 正式医疗记录仍需医生判断、确认与签署。
产品切入：按任务控制数据 + 医生最终确认 + Eval 回归

02 · Product Strategy

围绕患者诊前与医生接诊两类任务设计产品方案

患者侧重点是用尽可能低的交互成本完成信息采集、分诊和挂号；医生侧重点是复用同一份诊前信息完成接诊准备。围绕这两类任务，我把问诊深度、结果稳定性、数据使用范围和医生责任拆成四个产品设计原则。

DECISION 01

不同患者使用不同问诊深度

症状明确的用户更在意快速完成分诊，复杂病例则需要补充更多病史和风险信息。

产品设计：快速模式控制轮次完成核心信息采集；深度模式继续补齐关键病史与风险信息，避免所有患者都承担同样的问诊成本。
DECISION 02

重要结论先保证稳定，再追求表达自然

报告数值、趋势、信息状态和安全条件必须前后一致；症状理解、追问和解释则需要自然语言能力。

产品设计：可直接计算和判断的部分由程序处理，模型负责理解与表达；关键安全条件设置明确兜底。
DECISION 03

医疗数据按任务控制使用范围

不同功能真正需要的数据不同，不能因为调用模型就默认发送完整病历或原始报告。

产品设计：原始数据先在本地完成解密、结构化和去标识化，再根据预问诊、报告解读或病历草稿的具体任务提供必要字段。
DECISION 04

AI 先整理，医生完成最终确认

AI 的价值是减少信息整理与文档准备，而不是替代医生完成诊断和正式记录。

产品设计：AI 输出问诊摘要、趋势结论和病历草稿，医生核对、修改后形成正式病历并承担最终判断。

03 · Core Product Case

完成“预问诊—科室推荐—一键挂号”闭环

这一模块承担患者进入就医流程前的信息采集与分诊决策：先补齐关键症状、病史和风险信息，再结合科室映射生成就诊建议；问诊结束后把推荐科室作为后续挂号入口的默认建议，用户确认后直接进入挂号流程。

ASK

补齐真正缺失的信息

读取用户已经主动说明的内容，下一轮只补问仍缺失且会影响分诊的症状、病史和风险信息。

REMEMBER

记住已经说过和问过的内容

区分“用户已经说过、问过但不知道、拒绝回答、仍需继续补充”，避免把“不知道”当成“没问过”反复追问。

TRIAGE

把问诊结果转成科室建议

基于当前已确认信息生成结构化问诊摘要和科室推荐，让对话结果能够直接支持下一步就医决策。

CONVERSION

推荐结果直接进入挂号

将推荐科室作为挂号入口的默认建议，用户确认后进入对应挂号流程，减少再次搜索科室和重复选择。

PRODUCT FLOW

用户主诉 → 关键信息补全 → 科室推荐 → 用户确认 → 一键挂号

对话结果直接连接后续就医动作

① 用户主诉读取用户已主动提供的信息，确定本次问诊目标。
② 确认还缺什么结合知识与当前状态判断哪些关键信息仍未获得。
③ 多轮追问每轮只推进仍未解决的信息，并记录用户回答状态。
④ 安全检查出现明确危险信号时切换风险提醒与就医建议。
⑤ 科室推荐形成问诊摘要与可执行的科室建议。
⑥ 一键挂号用户确认推荐后进入对应挂号流程，问诊结果同步给医生侧复用。

ITERATION

预问诊策略的三轮迭代

阶段做了什么发现的问题调整后的判断方式
V1 · 固定必问提前列出必须补齐的关键信息，要求模型按清单追问。模型可以靠多问提高覆盖；用户已经主动说过的信息仍可能被重复询问。除了看“有没有问到”，开始同时看信息是否真正拿到、是否重复问和是否浪费轮次。
V2 · 知识检索 + 问诊计划先根据当前症状检索相关知识，再生成本轮应该追问的内容。检索到什么会直接影响后续问题，知识不相关或遗漏都会带偏问诊。单独验证检索和问诊计划；RAG 专项 Must-Ask 命中率由 64.21% 提升至 82.00%。
V3 · 记住每条信息的状态每轮都记录“用户已经说过什么、哪些还没问清、哪些问过但用户不知道、哪些用户拒绝回答”，下一轮只补真正还缺的内容。如果不区分这些情况，系统会重复问已经知道的信息，或者把“用户不知道”误当成“系统还没问”。评测从“某句话有没有被问出来”升级为“关键情况最后有没有补齐、系统有没有正确记录用户的回答状态”。
04 · Doctor Workflow

用报告分析与病历草稿减少医生信息整理

患者侧产生的问诊信息继续服务医生接诊：历史报告先由程序完成对齐和趋势计算，再由模型解释；病历草稿直接复用已经确认的问诊事实，并保留“不知道 / 未确认”等状态，减少医生从零整理信息的工作。

LONGITUDINAL REPORT

历史检验报告纵向分析

原流程逐份打开历史报告 → 手动找同类指标 → 比较数值、单位和参考范围 → 自己总结变化。
产品流程患者选择多次同类报告 → 本地完成指标对齐和趋势计算 → 输出关键变化与趋势摘要。
为什么这样分工单位、数值变化和趋势可以直接计算，优先交给程序；模型负责把结构化结果解释成患者和医生容易理解的语言。
验收标准数值和趋势要与原始报告一致；关键变化不能漏；解释中不能出现报告里没有的数据或结论。
DOCTOR DRAFT

医生病历草稿

原流程接诊后重新整理主诉、现病史、既往信息，再按病历结构书写。
产品流程复用预问诊结构化事实和历史记录 → 生成病历参考草稿 → 医生查看、修改和确认 → 形成正式病历。
信息边界草稿只能使用已有来源；用户说“不知道 / 未确认”的信息继续保留为不确定状态，不能自动写成肯定或否定事实。
验收标准关键字段不能漏；每条信息能找到来源；不能擅自补写症状、病史或诊断；医生能够快速核对和修改。

05 · Eval & Iteration

TRACE BAD CASE

单轮检索正常 → 多轮上下文漂移 → Trace 定位 Query Construction → State-aware Query → 回归验证

腹痛患者进入多轮问诊后，患者第二轮只回答“用了药”，旧逻辑直接把最新一句话当成检索 Query，导致主诉“腹痛”被丢失，后续知识与追问开始偏离当前场景。

BEFORE · USER IMPACT

优化前：后续问题逐渐偏离主诉

患者回答“用了药”后，系统围绕这句话重新检索，原本的“腹痛”上下文变弱；后续更容易召回无关知识，并影响追问、风险判断和科室推荐。

AFTER · USER IMPACT

优化后：每一轮都围绕当前主诉推进

系统持续带上“腹痛 + 已确认事实 + 当前问诊任务”，即使患者只回复一句短答案，下一轮仍围绕腹痛场景继续补齐关键信息。

回归验证Multi-turn Stability
验证逐轮检查 Query 与检索结果是否持续围绕腹痛。
结果连续多轮均保留主诉；即使用户最后回答“没有更多补充”，检索也不会退化成这句话本身。
EVALUATION LOGIC

评测先看安全和任务，再看体验；Trace 只用于定位原因

评测层主要看什么产品用途
安全是否漏掉危险信号、给出危险或越界建议。决定该 Case 是否可以进入正常业务流程。
任务完成关键信息有没有问清、科室推荐和必要结果是否完成。判断一次预问诊是否真正完成产品承诺。
使用质量是否重复问、问了无关问题、信息记录是否准确。比较不同版本通过任务门槛后的体验差异。
TraceQuery、检索、规划、执行与输出等中间过程。找到失败发生在哪一层，再做针对性优化和回归。
06 · My Role & Roadmap

我负责的核心产品工作与后续产品验证

从需求判断、核心流程设计到评测迭代，我主要负责把患者端和医生端的任务拆成可落地产品方案，并通过固定 Case 验证 AI 是否稳定完成关键任务。

需求与产品定位围绕患者问诊与挂号不便、隐私顾虑和医生病历整理耗时，梳理患者端与医生端核心场景，确定预问诊、挂号转化、报告分析和病历草稿的产品优先级。
预问诊与分诊链路设计设计快速 / 深度问诊、多轮信息补全、科室推荐与一键挂号流程，并持续优化“问什么、什么时候结束、推荐结果如何进入下一步业务”。
医生辅助产品设计设计历史报告纵向分析和结构化病历草稿，将患者问诊与历史信息整理成医生接诊前可直接查看和核对的结果。
数据使用与责任边界结合原有加密能力设计按任务控制数据范围的处理方式，并明确 AI 辅助结果与医生正式判断、正式病历之间的责任边界。
评测与迭代机制构建覆盖预问诊、安全、报告和病历草稿的 Eval V1，通过固定测试集、Trace 和 Bad Case 回归定位问题，推动产品与 Agent 链路持续迭代。
P0

验证分诊建议能否真正提升挂号转化

核心假设：用户拿到科室推荐后，仍会在“选医生、选时间”上产生二次决策成本；如果继续结合排班、时间和用户偏好推荐，可缩短完成挂号的路径。
验证指标：科室推荐采纳率、问诊→挂号转化率、完成挂号时长。

P1

验证医生真正需要哪些接诊辅助信息

核心假设：医生更需要“接诊前快速获取可信信息”，而不是 AI 替代诊断；问诊摘要和病历草稿的价值取决于是否减少阅读与修改成本。
验证指标：草稿采纳率、平均修改量、接诊准备时间、重点信息查看率。

P2

把单次报告解读延伸为持续健康管理

核心假设：用户对报告的需求不只发生在一次解读，更需要知道指标长期怎样变化、什么时候需要复查。
验证指标：趋势回看率、复查提醒完成率、连续报告使用率与长期留存。
